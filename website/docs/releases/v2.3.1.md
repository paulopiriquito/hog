# HOG v2.3.1

A patch release for a sign-in that failed on its way back from the identity
provider. A person whose session had expired was sent to sign in, and the
callback answered `400 invalid authentication response` even though they had
done nothing wrong. Trying again usually worked. Nothing in the configuration
model changes.

## What went wrong

Every sign-in wrote its `state` into the same cookie, `hog_login`. A second
sign-in started before the first one returned overwrote it, so the first
callback carried a `state` the cookie no longer held, and HOG rejected it as
it should reject a forged one.

The second sign-in did not need a second tab. A browser fetches a page's
favicon on its own, outside any service worker, and sends the session
cookie with it. With the session expired, the auth gate redirected that
request to the login path like any other request to an `app` route, the
browser followed, and the login endpoint started a sign-in nobody would
ever finish. A single-page app served from a service worker cache makes this
likely: the shell loads without touching HOG, finds the session gone and
sends the person to sign in at about the moment the browser asks for the
favicon. The longer the person spends at the identity provider's login form,
the surer the favicon wins.

## Only a navigation starts a sign-in

The auth gate redirects an unauthenticated request on a required `app` route
to the login path only when the browser marks it `Sec-Fetch-Mode: navigate`.
A favicon, an image, a stylesheet, a script or a `fetch()` gets `401` instead.
A client that sends no Fetch Metadata, such as `curl` or an older browser,
keeps the redirect it had.

A script that fetched an `app` route without a session used to get a redirect
it could not follow, since the identity provider is on another origin. It now
gets a `401` it can act on.

## Each sign-in has its own cookie

The login cookie is now `hog_login_<id>`, where the id is derived from that
sign-in's `state`. The callback opens the cookie that belongs to the `state`
it was given and expires only that one, so two sign-ins in flight at once,
from two tabs or from anything else, both complete.

Every abandoned sign-in leaves a cookie behind for its ten minutes. When a
browser already carries five, the next sign-in clears them before writing
its own, so the `Cookie` header cannot grow without bound.

During a rolling upgrade a sign-in started on an older replica arrives with
a plain `hog_login` cookie. The callback still reads it.

## A lost sign-in no longer strands a signed-in person

When a callback cannot be matched to its sign-in (the login cookie is
missing, cannot be decrypted, or holds another `state`) and the browser
already has a valid session, another sign-in finished first. The callback
now redirects to `/` instead of answering `400`. Nothing from the unmatched
callback is used: no code is exchanged and no session is issued. A browser
without a session still gets the `400` it got before.

## Upgrading

Replace the binary or the image. A single-page app that relied on an `app`
route redirecting its own `fetch()` calls to the login path should check for
`401` and navigate to the login path itself, which is what it had to do
already for the redirect to be useful.
